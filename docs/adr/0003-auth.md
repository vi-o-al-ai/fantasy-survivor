# 0003. Authentication via Auth0 access tokens verified locally

Date: 2026-09-02
Status: Accepted

## Context

Accounts are handled by Auth0. The API runs on Lambda and should stay
stateless. Web and future mobile clients need the same auth path. Tests
and local development must not depend on an Auth0 tenant.

## Decision

- Clients obtain an RS256 access token from Auth0 with the API's audience
  and send it as a bearer token.
- The API verifies tokens itself against the tenant JWKS (cached), never
  calling Auth0 per request. Issuer, audience, expiry, and signature are
  all required; only RS256 is accepted.
- Authorization uses the `permissions` claim (Auth0 RBAC), checked by a
  `require_permission()` dependency. The API stores no user table for
  auth; user identity is the token `sub`.
- The verifier core takes a `KeyProvider`. Tests inject a static key;
  local development can use a JWKS file created by
  `scripts/mint_dev_token.py`. That mode is refused in deployed
  environments.

## Consequences

- Revocation is by token expiry only; keep access tokens short-lived
  (Auth0 default is fine).
- Any Auth0-issued permission change appears on the next token, not
  immediately.
- A mobile app uses the Auth0 native SDK and the same audience; no API
  change required.
