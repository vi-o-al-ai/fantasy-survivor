# 0006. CI/CD with GitHub Actions and OIDC to AWS

Date: 2026-09-02
Status: Accepted

## Context

Every phase already runs checks in GitHub Actions. Deploying needs AWS
credentials in CI, a build of two artefacts, and an ordering constraint:
the frontend must be built with the API URL that Terraform outputs.

## Decision

- **Auth:** GitHub OIDC federated into one IAM role, created by
  `infra/bootstrap`. No access keys stored anywhere. The role is
  `PowerUserAccess` plus IAM actions limited to roles prefixed with the
  project name.
- **Trigger:** push to `main` touching app or infra paths, or manual
  dispatch. A `deploy-dev` concurrency group serialises applies without
  cancelling one in progress.
- **Order:** build Lambda zip → `terraform apply` → read outputs → build
  frontend with `VITE_API_URL` → sync to S3 with immutable caching for
  hashed assets and `no-cache` for `index.html` → invalidate → smoke test
  `/health`.
- **Config:** non-secret values (Auth0 domain, audience, SPA client id,
  state bucket) are GitHub environment variables on a `dev` environment.
  A `prod` environment later reuses the same workflow with a different
  root and required reviewers.

## Consequences

- `terraform apply` runs unattended on `main`. Review happens on the pull
  request, where CI runs `fmt`/`validate`; adding a `plan` comment on
  PRs is the obvious next step once the deploy role exists.
- A broken deploy leaves Terraform state consistent (locking) and is
  rolled back by reverting the commit.
- Provisioning the Auth0 tenant itself stays manual for now. The Auth0
  Terraform provider can take that over when the tenant config grows.
